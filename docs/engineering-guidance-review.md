# 工程指导有效性审查

0.1.0 的目标是让重要工程决策有依据：明确结果、理解相关系统、观察真实行为、依据失败修正假设。交付质量与判断成本共同衡量；文档、命令和阶段数量不作为成功指标。

## 对旧体系的处理

| 原机制或缺口 | 0.1.0 的处理 | 可观察的作用 |
| --- | --- | --- |
| 固定工作流、阶段状态和 Hook | 删除，保留一个总 Skill 和按需指南 | 简单修复无需经过整套阶段 |
| 分支与活动任务绑定 | 删除，Spec 直接按目录独立存在 | 多会话可在同一分支创建不同 Spec |
| 文档与验证收据容易成为终点 | Spec 记录结果、证据范围与下一步 | 未运行和未得到人工反馈仍保持明确 |
| UI Evidence 缺少可比较参照 | 产品目标、现有组件、视觉与行为基线共同约束 | 能判断风格偏离、状态遗漏和交互中断 |
| 任务拆分偏向文件层次 | 按用户路径构建可运行切片 | 及早发现端到端契约问题 |
| 局部补丁掩盖状态和依赖问题 | 先定位状态归属、时序、不变量与消费者 | 旧响应覆盖、单位变化有明确反例 |
| 修复失败后继续堆补丁 | 记录假设、预测、实际结果与反证 | 下一次诊断改变信息来源或根因模型 |
| 长期上下文混入临时经验 | 元数据、概览、原文按需读取，经验保留依据 | 降低噪声，同时可追溯关键约束 |

## 吸收的工程方法

以下方法由腾讯、美团工程实践启发，具体规则是本项目对轻量工具的取舍，不代表复刻其平台或承诺同等效果。

- 腾讯 [大规模研发实践](https://news.qq.com/rain/a/20261016A0AYDU00)：复用既有实现，提前明确验收参照，检查测试能否发现目标缺陷。落实在 Product、UI、Verification 指南。
- 腾讯 [研发全流程实践](https://news.qq.com/rain/a/20261009A0A0JA00)：关注最终交付，渐进形成可运行结果，反馈过期知识。落实在 Slices、Knowledge 指南。
- 腾讯 [故障排查实践](https://news.qq.com/rain/a/20260923A0A8W700)：结合项目事实、源码与运行证据，检验候选根因。落实在 Diagnosis 指南，不引入多 Agent 调度。
- 腾讯 [上下文工程实践](https://news.qq.com/rain/a/20260914A0B89Z00)：区分规则、任务状态、历史、知识与工具结果。落实为短入口、独立 Spec、知识索引与按需正文。
- 美团 [分布式存储中的 AI Coding](https://tech.meituan.com/2026/10/29/AI-Coding-IN-Distributed-Storage-System.html)：区分源码支持、运行证实、已推翻与待验证；测试需要形成反例。落实在 System、Diagnosis、Verification 指南。
- 美团 [Agent 评估白皮书](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html)：评估方法的进步与被评估对象的进步分别考察。落实为固定场景、对照实验和独立的工具测试，不把结构检查当行为提升。
- 美团 [LOOP AutoResearch](https://tech.meituan.com/2026/10/22/LOOP-AutoResearch.html)：将优化写成可检验假设，限定实验成本与停止条件。落实为 Slices 的性能实验方法，不增加循环控制器。

## 四种高风险场景

| 场景 | 关键判断 | 验收依据 |
| --- | --- | --- |
| UI 重构 | 已有视觉体系、核心任务、状态和布局边界 | 实际页面的前后参照、交互路径、移动端与键盘操作 |
| 复杂状态 | 唯一状态归属、请求时序、取消和重试 | 明确的乱序、失败、重入反例及真实路径 |
| 跨模块变更 | 单位、接口、生产者与消费者共同约束 | 端到端结果与相关回归行为 |
| 持续返工 | 当前根因是否被证据支持 | 能解释原症状、拒绝错误假设并证明修复有效 |

本次实现验证安装、上下文读取、并行 Spec、错误输入和固定场景的反例有效性。尚未开展真实模型的有无指导对照实验，因此不声称已量化提高 Codex 的成功率。评估方式见 [行为评估](behavior-evaluation.md)。
